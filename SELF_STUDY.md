# SELF_STUDY — Шаблони, статичні файли та CSRF

Звіт до ПР №2.5. Усі результари нижче отримані власноруч на власному комп'ютері
(Django 6.1.1, Python 3.14, SQLite, запуск через `manage.py runserver`).

---

## Урок №1. HTML у назві товару

**Що робив.** Додав товар з назвою `<script>alert(1)</script>` через форму
додавання, потім відкрив «Переглянути код сторінки» на сторінці списку.

**Результат.** Скрипт **не виконався**, спливаючого вікна з `alert(1)` не було.
У коді сторінки тег екранувався:

```html
<td class="product-name">&lt;script&gt;alert(1)&lt;/script&gt;</td>
```

Замість `<` та `>` браузер отримав сутності `&lt;` і `gt`, тому це вже не HTML-тег,
а текст. Те саме сталося з повідомленням про успішне збереження.

**Чому так.** Django екранує значення за замовчуванням (`autoescape`), і це
робить кожен `{{ ... }}`, якщо не вказати `|safe` або не вимкнути екранування для
конкретного шаблону. Тому дані з бази не можуть стати виконуваним кодом.

**Перевірка тестом.** `ProductListTests.test_product_name_is_escaped_not_executed`
створює такий товар і перевіряє, що сирої рядки `<script>alert(1)</script>` у
відповіді немає, а є екрановані сутності.

## Урок №4. `DEBUG = False` і статичні файли

**Що робив.** Тимчасово виставив `DEBUG = False` у `config/settings.py`,
перезапустив `runserver` і відкрив сторінку.

**Результат.** HTML сторінки віддався нормально (`200`), але запит до
`/static/catalog/css/style.css` повернув **`404 Not Found`**. Сторінка стала
голою: теги та таблиця є, а стилі зникли.

Причина: `runserver` — це тільки сервер для розробки, і він видає файли з
`STATIC_URL` **лише тоді, коли `DEBUG = True`**. У режимі розробки це зручно
(файл підхоплюється з папки одразу після збереження). У «бойовому» режимі Django
не бере на себе роль вебсервера для статики.

**Як перевірити, що справа саме в цьому:**

| Крок | Команда | Результат для CSS |
| --- | --- | --- |
| `DEBUG = True` | `runserver 8000` | `200` |
| `DEBUG = False` | `runserver 8000` | **`404`** |
| `DEBUG = False` | `runserver 8000 --insecure` | `200` |

Прапорець `--insecure` повертає роздачу статики — це зручно, але заборонено
у production. Правильний шлях: `python manage.py collectstatic` (у мене
скопіювалося **131 файл** у `warehouse/staticfiles/`), далі вебсервер (Nginx,
Apache) віддає файли з `STATIC_ROOT` напряму. Для цього в `settings.py` додано
`STATIC_ROOT`.

**Побічний эффект, який я не очікував.** Після `DEBUG = False` запит до будь-якої
сторінки почав повертати **`400 Invalid HTTP_HOST header`**. Причина окрема:
з `DEBUG = False` Django більше не підставляє `localhost` у `ALLOWED_HOSTS`
автоматично, а там порожній список. Довелося тимчасово додати
`ALLOWED_HOSTS = ['127.0.0.1', 'localhost']`. Після експерименту
`DEBUG = True` і порожній `ALLOWED_HOSTS` повернуто.

Після експерименту налаштування повернуто до початкового стану.

## Урок №5. CSRF і відхилений запит (403)

**Що робив.** У DevTools на сторінці форми знайшов токен — і в HTML, і в cookies.
Потім надіслав POST без токена.

**Результат.** У формі є приховане поле, а в cookies — однойменний `csrftoken`:

```html
<input type="hidden" name="csrfmiddlewaretoken" value="...">
```

| Дія | Результат |
| --- | --- |
| POST **із** токеном | `302` → `/`, товар створено, показане повідомлення |
| те саме після F5 | повідомлення **зникло** (показано один раз) |
| POST **без** токена, cookie є | **`403`**, у лозі `Forbidden (CSRF token missing.)` |
| POST без токена і без cookie | **`403`**, у лозі `Forbidden (CSRF cookie not set.)` |

Текст сторінки 403: заголовок **«403 Forbidden»** і рядок
**«CSRF cookie not set.»** (або «CSRF token missing.» — залежно від того, чи
була cookie). Далі йде великий блок підказок від Django: перевірте, що браузер
приймає cookie, що в шаблоні є `{% csrf_token %}` і що у вас увімкнено
`CsrfViewMiddleware`. Цей блок видно лише при `DEBUG = True`; у production
показують тільки коротке повідомлення.

**Чому запит відхилено (своїми словами).** Браузер сам додає cookies до запитів
на сайт, і саме на цьому тримається авторизація. Але cookie браузер додає і до
запиту, який надіслав зовнішній сайт: якщо користувач відкрив таку сторінку, то
її JavaScript може непомітно відправити POST на наш сервер, і cookie поїде разом
із запитом — сервер побачить «залогіненого користувача», хоча він нічого не
клав. Щоб відрізнити запит із нашої справжньої форми від підробленого, Django
просить додати в форму випадковий секретний токен, який зберігається в cookie
`csrftoken`. Наш шаблон додає цей токен у форму тегом `{% csrf_token %}`, і
обидва значення мають збігатися. Якщо токена немає або він не збігається —
значить, форми нашого сайту не ініціював сам користувач, тож запит відкидається
з кодом 403, щоб нічого не змінилося.

**Два способи злов'язати** (з відео PortSwigger): злов'ястий сайт підкладає
користувачеві форму, яка POSTить на наш `/products/add/`, і браузер додає cookie
автоматично. З `{% csrf_token %}` такий запит падає з 403; без нього — succeeds.

**Перевірка тестами.** `ProductCreateTests.test_post_without_csrf_token_is_rejected`
створює клієнт із `enforce_csrf_checks=True`, надсилає POST без токена й очікує
`403` та `Product.objects.count() == 0`.

## Яке джерело допомогло найбільше

- Офіційна документація Django — розділи про шаблони, `{% static %}` і CSRF.
  Найпростіше було читати про `{% extends %}` / `{% block %}` / `{% include %}`:
  там одразу видно різницю між `base.html` і дочірнім шаблоном, і не треба
  вгадувати, що `{{ block.super }}` існує.

## Що лишилося незрозумілим

1. **Чи треба `{% csrf_token %}` на кожній POST-формі, чи достатньо одного разу
   в `base.html`?** Я поставив його всередині самої форми в `product_form.html`,
   бо тег має бути саме всередині `<form>`. Не зрозумів, чи виправданий такий
   підхід, коли форм багато — чи краще винести їх у `partials/`, як ми зробили
   для меню й повідомлень.
2. **`|safe` і `mark_safe`.** Розумію, що вони вимикають екранування, і саме
   тому їх небезпечно застосовувати до даних від користувача. Але не зрозумів,
   який саме «правильний» випадок їх використання: якщо в базі лежить, скажімо,
   HTML-опис товару від редактора — то це треба проганяти через `|safe`? Чи
   краще зберігати в базі чистий текст і не дозволяти HTML узагалі?
3. **`STATIC_URL` без слеша.** У `settings.py` стоїть `STATIC_URL = 'static/'`
   (так генерує `startproject`), і я спершу подумав, що це помилка. Виявилося,
   Django сам додає слеш на початку через `_add_script_prefix`. Не зрозумів,
   чи варто писати `/static/` явно, чи краще залишити як згенеровано.
4. **`{% product_count %}` робить запит у базу під час рендерингу шаблону.**
   Це нормально для навчальної задачі, але я так і не зрозумів, коли це починає
   бути проблемою і що тоді робити замість цього (кеш? `select_related`? просто
   передавати лічильник із view?).
5. **Модель `Product` узяв з ДЗ №2.4.** Не пам'ятаю, чи там були саме такі поля
   й така назва, тому створив модель «як було зручно»: `name`, `description`,
   `price`, `quantity`, `created_at`. Якщо в ДЗ №2.4 модель була іншою, треба
   звірити — інакше наступні ПР можуть на неї спиратися.
